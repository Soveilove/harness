# Sovei 产品功能需求

**版本**：0.1 Draft
**日期**：2026-08-18
**定位**：待重新评估的产品功能池，不代表已立项、已承诺或当前开发顺序。
**依据**：产品需求文档、产品验证计划、工作流设计和当前源码观察。

## 1. 使用规则

本文件替代原开发清单，记录“可能值得做什么”，不直接决定“现在做什么”。

每项需求在开发前必须重新完成：

1. 确认真实用户问题；
2. 确认当前问题仍然存在；
3. 明确最小产品结果；
4. 明确不做什么；
5. 设计独立验收场景；
6. 通过产品评审后，才创建新的 Feature。

本文件中的状态含义：

- **候选**：有产品假设，尚未证明值得开发；
- **待验证**：需要通过 S0/S1/S2 或真实用户任务验证；
- **暂缓**：当前不进入开发；
- **已取消**：不再作为产品方向保留。

## 2. 当前产品前提

Sovei 的核心产品目标是：

> 帮助用户从不完整或复杂的需求走向有证据的可验证交付，并在跨会话时恢复唯一合法下一步。

因此，所有候选功能都必须回答：

- 它减少了哪一种用户不确定性？
- 它改变了哪个用户决策或交付结果？
- 没有它时用户会遇到什么真实问题？
- 它是否会增加比收益更多的文档、等待或操作负担？

在第一轮产品验证完成前，不启动高级扩展功能。

## 3. P0：状态与需求进入基础

### FR-001 Workflow 唯一状态源

**状态**：候选，工程基础

**用户问题**：用户跨会话恢复工作时，无法确定事件流、YAML、Markdown 哪一个才是真实状态，容易重复工作或错误推进。

**产品目标**：为新 Feature 提供一个可版本化、可审计、可恢复的结构化状态源。

**功能要求**：

- 新 Feature 使用 `workflow-state.json` 保存当前状态；
- 状态包含身份、schema 版本、阶段、revision、历史和下一步信息；
- 状态更新具备原子写入和陈旧写入拒绝；
- 非法、损坏或过期操作明确失败；
- 不从 Markdown、旧 YAML 或旧事件恢复新状态；
- 历史 Feature 不迁移、不回放、不兼容。

**不包含**：split 聚合、Quick 路由、旧数据迁移、Graph Coding。

**验收方向**：新会话可以仅依靠结构化状态恢复当前目标、阶段、风险和唯一下一步；失败操作不破坏最后有效状态。

**重新评估条件**：先用 S1 普通 Feature 和 S2 长周期需求验证状态是否真的减少恢复成本。

### FR-002 需求理解与澄清工作台

**状态**：候选，产品核心

**用户问题**：用户往往知道想解决什么，但无法一次性描述目标、范围、约束和验收；系统要么直接猜测，要么简单阻塞。

**产品目标**：让信息不足的需求可以继续澄清，而不是丢失或被迫进入错误流程。

**功能要求**：

- `explore` 先区分可自动发现的事实和必须由用户判断的内容；
- 生成结构化 `clarification-pack`；
- 每个问题说明缺口类型、原因、答案格式和影响；
- 支持用户部分回答、多轮回答和回答审计；
- 保留已答、未答、假设、证据和轮次；
- 回答后重新评估，而不是直接强行推进；
- 区分 `clarifying`、`blocked` 和 `cancelled`。

**不包含**：让模型代替用户做产品决策，不允许澄清过程直接修改业务代码。

**验收方向**：用户不需要重复提供已经确认的信息，回答后能得到唯一合法下一步。

**重新评估条件**：通过一个信息不完整的真实需求回放，记录问题质量和用户负担。

### FR-003 Explore 路由与轻量路径

**状态**：候选，依赖 FR-001/FR-002

**用户问题**：简单需求被迫进入重流程，或者用户在需求尚未理解前直接启动 Quick，导致范围和风险失控。

**产品目标**：所有自然语言需求先经过理解，再根据风险选择合适路径。

**功能要求**：

- `explore` 输出结构化 `route`、理由、允许路径、风险信号和唯一 `nextAction`；
- 小范围、低风险、目标明确的需求才可进入 Quick；
- 普通需求进入正式 Feature；
- 多个独立交付面进入 `split-candidate`，先做产品决策；
- 信息或权限不足进入 `clarifying` 或 `blocked`；
- Quick 执行中发现范围扩大时升级到正式流程。

**不包含**：裸 Quick 入口、伪 Feature、在 Quick 内补齐完整正式流程。

**验收方向**：S0 小修复不过度阻塞，复杂需求不被错误地走捷径。

**重新评估条件**：完成 S0 和 S1 路由对比，证明路径选择减少而非增加用户负担。

## 4. P1：复杂需求与效率

### FR-004 Split 父子交付聚合

**状态**：暂缓，依赖 FR-001/FR-003

**用户问题**：一个 Feature 拆成多个 change 后，父层、子层和完成状态可能漂移，出现伪完成或重复汇聚。

**产品目标**：只有在确实存在多个独立交付面时，提供清晰的父子执行范围和聚合门禁。

**功能要求**：

- 明确 `mode`、`aggregation` 和 execution scope；
- 父 Feature 和 Sub-change 的状态边界明确；
- 子 change 独立验证并保留证据；
- 未全部完成时父层不能伪造完成后续阶段；
- 全部完成后父层只进行一次真实聚合。

**不包含**：为了展示拆分能力而强行创建多个 change。

**验收方向**：真实多交付需求回放中，不出现重复 `learn`、双重 merge 或隐式阶段跳跃。

**重新评估条件**：S2 或真实多交付需求证明单 Feature 已无法清晰管理范围。

### FR-005 真增量扫描

**状态**：候选，待验证

**用户问题**：当前 changed files 只在部分消费端过滤，底层仍执行全量扫描，用户无法获得可信的性能收益。

**产品目标**：没有相关变化时复用已有结果，有关键配置或依赖变化时安全回退到全量扫描。

**功能要求**：

- 区分“消费端过滤”和“真正跳过扫描”；
- 建立扫描输入、产物和依赖的变更判定；
- 无变化时复用可验证的旧产物；
- 关键配置、依赖或扫描器版本变化时触发全量回退；
- 输出扫描模式和复用原因。

**验收方向**：独立测试证明无变化不会重复执行全量工作，且回退条件不会漏扫。

**重新评估条件**：先取得真实项目扫描耗时和重复扫描数据。

### FR-006 知识进入价值门槛

**状态**：候选，待验证

**用户问题**：所有观察都进入知识库会造成知识膨胀、噪声增加和后续决策污染。

**产品目标**：只有有证据且具有复用价值的内容才进入知识生命周期。

**功能要求**：

- 定义最少证据、最小复用次数或其他可解释门槛；
- 保留 candidate → pending → stable 的人工治理；
- 说明被拒绝或延迟入库的原因；
- 不因单次偶然观察直接晋升稳定知识。

**验收方向**：知识库规模、复用率和错误命中率可被独立观察。

**重新评估条件**：先收集真实知识复用数据，不为晋升制造样例。

### FR-007 架构信号接入交付流程

**状态**：候选，待 S2 验证

**用户问题**：架构扫描是独立命令，需求范围、实施方案和验证过程看不到模块指标与架构债务。

**产品目标**：让架构风险在真实开发流程中被及时发现，而不是只在用户主动运行命令时出现。

**功能要求**：

- 在相关阶段提供模块指标和债务信号；
- `scope/plan/converge/verify` 能看到与当前需求相关的架构事实；
- converge 能识别新增高风险热点；
- verify 可按项目策略执行架构门禁；
- 自动登记必须保留人工确认，不得凭提示直接晋升稳定债务。

**不包含**：替用户做不可逆的架构决策。

**验收方向**：S2 场景中能发现独立测试无法发现的影响面或架构风险。

**重新评估条件**：真实跨模块需求出现架构遗漏证据后再立项。

## 5. P2：集成和体验扩展

### FR-008 结构化 CLI/Agent 输出

**状态**：候选，按真实消费需求启动

**用户问题**：IDE Agent、脚本和 CI 无法稳定消费当前阶段、风险、证据和下一步，只能解析自然语言。

**产品目标**：为机器消费者提供稳定 JSON 契约，不改变核心工作流语义。

**功能要求**：补齐 workflow、knowledge、workspace 等关键命令的结构化输出；包含状态、下一步、风险、错误和证据引用。

**验收方向**：至少一个真实 Agent 或 CI 消费者无需文本解析即可完成闭环。

### FR-009 Agent 宿主差异化初始化

**状态**：候选，按真实安装需求启动

**用户问题**：不同 Agent 宿主支持的命令、技能和配置方式不同，一刀切安装会产生无效配置。

**产品目标**：根据宿主能力安装适合的适配器、slash command、文本规则或技能包。

**功能要求**：提供宿主选择、差异化安装和配置记录；保留非交互参数路径。

**验收方向**：至少两个真实宿主完成初始化，生成的配置可用且互不污染。

### FR-010 通用 CLI 交互原语

**状态**：候选，按真实交互需求启动

**用户问题**：当前交互面板能力散落在适配器选择器中，无法复用于 Agent、Skill 等初始化场景。

**产品目标**：提供零依赖、可测试、支持 TTY 与非交互环境的 `select` / `multiselect`。

**验收方向**：交互模式和 CI/脚本模式都不会阻塞，并且输入结果可复现。

### FR-011 外部 Skills 受控吸收

**状态**：暂缓，先审计

**用户问题**：外部 Skill 的来源、权限、版本和私有耦合不清晰，直接吸收会污染产品边界。

**产品目标**：只吸收经过授权、去私有化和独立验证的通用方法。

**功能要求**：逐项审计来源、权限、版本、引用和适用阶段；支持按需 reference 加载；外部 Skill 不得改写核心状态和阶段契约。

**验收方向**：安装、升级、回放和失败隔离均可说明，且不增加运行时不透明依赖。

## 6. P3：战略候选

以下需求当前只保留为产品假设，不进入开发：

- **FR-012 统一关系模型**：连接业务能力、代码入口、模块、规则、Spec、Task 和 Evidence；只有当现有文件关系无法支持真实任务时再评估。
- **FR-013 MCP 工具层**：只有出现明确的 MCP 消费者和工具契约后再评估；当前 capability 字段不代表产品需求。
- **FR-014 联邦多 Hub**：只有单 Hub 无法满足真实团队或多工程协作时再评估。
- **FR-015 Python 等额外语言扫描**：只有真实项目和明确扫描缺口出现时再评估。
- **FR-016 CI/CD 集成模板**：依赖结构化输出，并由真实 CI 使用场景驱动。
- **FR-017 Usage 脱敏导出**：只有出现团队评测或共享需求时再评估。
- **FR-018 子 Agent 并行增强**：只有数据量和执行耗时证明并行收益后再评估。
- **FR-019 外部 Skills 生命周期管理**：只有出现稳定供应源、版本差异和升级需求后再评估。

## 7. 删除、合并和立项规则

- 没有真实用户问题的需求删除；
- 解决同一用户问题的多个候选合并；
- 只有通过独立场景验证的候选才创建 Feature；
- 技术实现项不能单独成为产品需求，必须挂靠用户结果；
- 旧 Feature、旧事件、旧 YAML 不作为新需求的兼容约束；
- 完成一个需求后重新评估剩余需求，不自动按本文件顺序开发。

## 8. 当前唯一下一步

先完成产品验证计划中的 S0、S1、S2 场景记录，再根据证据决定是否立项 `FR-001`、`FR-002` 或 `FR-003`。在此之前，不创建新的实现 Feature。
