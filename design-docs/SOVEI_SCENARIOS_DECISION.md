# Sovei CLI — 场景一/场景二 设计决策记录

> 状态：Draft（待收敛落地）
> 创建日期：2026-08-06

> 性质：本文件固化对**通用用户项目使用 CLI**（场景一）与**多分支/多工程协作**（场景二）暴露问题的架构基准。不是运行时能力清单，实现需另行验证。
> 背景：用户以个人 a/b/c 三工程并行起步，人工 + AI 经"中转站"同步分发，欲 cli 化为可规模化的 SOP（未来被大量开发者、多分支合并 test/master 使用）。

---

## 1. 核心结论

1. **场景一**：通用用户项目里，spec/工作流文件按"可重建性 + 语义价值"分四层，进 git 与否分层决策，并靠"AI 判断 + 确定性边界 + 人工闸门"自动沉淀。
2. **场景二**：多分支/多工程用**联邦星型拓扑**（每主干一个对账中枢），核心是 **merge preflight（合并前语义冲突预检）**。
3. **贯穿两场景的灵魂**：**执行纪律链**——四个强制卡点（基线隔离 → 判定样例 → 规则清单 → 自检门），解决"规则清楚但 AI 执行出错"的系统性问题。
4. 设计权分配依据**可逆性**：会毁掉系统的东西交给规则；搞错了能改的东西交给 AI（判断带理由、进事件流）；质量闸门交给人工。

## 2. 场景一：通用用户项目的 spec 文件与 git

### 2.1 用户真实痛点

- 多开发协同，spec 文件快速"迭代满"，git 历史被刷。
- AI 无法从堆积的 spec 里提取有用的东西。

### 2.2 分层决策（进 git 与否）

| 层 | 文件 | 进 git | 理由 |
|---|---|---|---|
| ① 事实源 | `workflow-events.jsonl`、`wayfinder-events.jsonl`、`decision-tickets/*.json`、`redline-events.jsonl` | **必须** | 状态机/决策唯一事实源，删了不可复现，AI 无权归档 |
| ② "为什么" | `decision-log.md`、`reconciliation.md` | **必须** | 承载历史决策语义，跨 Feature/跨分支还原现状 |
| ③ 知识沉淀 | `harness/project/knowledge/*.json`、`redlines.json` | **必须** | AI 复用主体，CLI 提取 candidate + 人工 promote |
| ④ 过程产物 | `spec.md`/`plan.md`/`tasks.md`/`scope.md`/`coverage-matrix.md` 细节 | **收敛后归档** | 一次性消耗品，Feature 收敛后由 CLI 归档/精简 |
| 派生视图 | `wayfinder.md`、`workflow-state.yaml`、`wayfinder.json`、`redlines.md` | **忽略** | 可从事实源重建，进 git 只刷屏 |

> 注意：事实源 ≠ spec 内容。`workflow-events.jsonl` 是机器状态，不是 spec 的 markdown 详情。

### 2.3 "CLI 化自动沉淀"形态（防止噪声知识）

```
spec/reconciliation 过程产物
  → CLI 在 learn/sync 自动提取（带理由、进事件流）
  → knowledge/*.json 的 candidate
  → 人工 promote（候选→stable）
  → stable 知识（AI 真正复用）
```

**关键**：
- 自动提取解决"AI 提取不出有用的东西"。
- 人工 promote 解决"自动提取的噪声"，**硬性引用既有原则："不自动将单次观察升级为稳定规则"**。
- 提取需设**复用价值阈值 + 最少证据**，防止"spec 膨胀变成 knowledge 膨胀"。

### 2.4 决策权分配（按可逆性）

| 决策 | 可逆性 | 归属 |
|---|---|---|
| 事实源/派生视图是否保留 | 不可逆 | **规则锁定**，AI 无权 |
| 这条知识值不值得沉淀 | 可逆 | **AI 判断**（带理由+事件流） |
| 过程性 spec 是否归档 | 部分可逆 | **AI 判断**（归档进 history，可找回） |
| 知识是否升 stable | 不可逆 | **人工确认** |

### 2.5 场景一当前落地差距（2026-08-07 核对，基于 2.5.6 源码）

> 本节记录「场景一」设计意图与 Sovei 当前真实能力的差距，作为待开发清单。能调用的能力以源码/证据为准。

| 设计意图 | 当前落地 | 差距 |
|---|---|---|
| 知识自动沉淀（learn → candidate → 人工 promote） | ✅ 已实现：`reconcile.ts` learn 自动对账、knowledge 生命周期、`knowledge promote/deprecate` | 无 |
| "单次观察不自动晋级 stable" | ✅ 已实现（candidate→pending→stable 需多证据） | 无 |
| 事实源不可删（事件流） | ✅ 已实现：`workflow-events.jsonl`/`wayfinder-events.jsonl` 为事实源，AI 无权归档 | 无 |
| 过程产物收敛后归档 | ⚠️ 部分：`apply-change`/`reopen` 时 `archiveInvalidatedArtifacts` 归档到 `history/revision-N/` | **Feature 收敛后主动归档未实现**（当前只在变更/重开时归档，不是 learn/sync 收敛时主动归档/精简） |
| spec 四层进 git 分层决策 | ❌ 未实现 | **无 CLI 化的分层 git 策略命令**（哪些进 git、哪些 ignore 未固化为可执行规则/模板） |
| 知识提取「复用价值阈值 + 最少证据」防膨胀 | ❌ 未实现 | **learn 对账无复用价值阈值门槛**，依赖阶段提示词约束，非引擎强制 |

**结论**：场景一已具备知识沉淀闭环，缺口集中在「spec 分层 git 策略固化为命令/模板」「Feature 收敛后的主动归档」「知识提取的确定性阈值」。这是场景一未落地的部分。

## 3. 场景二：多分支/多工程协作

### 3.1 用户真实痛点

- 并行 a/b/c 三工程，发现需求冲突、代码变动冲突、业务红线不同。
- 规模化后：千千万万开发者、无数 feature 分支合并进 test/master，产生大量信息冲突。
- **真实致命案例**：重构模块放 test，产品上线当天说"新模块有风险不上，旧模块同步部分新模块规则，后续再上"→ 需求被撕裂，AI 执行一直出错（缺漏/理解不了），Speckit/OpenSpec 都救不了。

### 3.2 架构：联邦星型拓扑

- 个人用单一 hub（星型）足够，但规模化后纯星型有瓶颈（单点故障 + 对账爆炸）。
- **升级为联邦星型**：每个主干（test/master）各有一个"对账中枢"，feature 分支先合并到所属主干中枢，主干间再合并；每层对账复用同一套 SOP，仅作用域不同。

```
feature-A ──► test分支中枢 ──┐
feature-B ──► test分支中枢 ──┼──► master分支中枢 ──► 全局
feature-C ──► master分支中枢 ──┘
```

### 3.3 三样东西该不该过中枢

| 东西 | 处理 |
|---|---|
| 知识（踩坑/规则/代码地图/偏好） | **共享**：有价值知识晋升到中枢，分发所有工程 |
| 业务红线（redlines） | **部分共享**：公共红线过中枢；工程专属红线**必须隔离**（A 的红线不能强加 C） |
| Feature/spec 状态 | **不共享**：各工程需求演进，绝不经过中枢（现状已正确） |

**空缺**：红线现为全局单例，需加 `scope`/`owner`/`branch` 字段，按分支生效，同步做作用域过滤。

### 3.4 核心机制：merge preflight（合并前语义冲突预检）

git 只懂文本冲突，不懂业务语义。合并前必须跑语义预检：

```
准备合并分支X → 主干Y
  ① 文本冲突检查（git 自带）
  ② 业务语义冲突检查（redlines + knowledge + coverage-matrix）
     - 同一业务域是否被两分支定义了相反红线？
     - 同一代码表面是否被两分支 coverage 命中且改法矛盾？
     - 两分支的知识/决策是否互相矛盾？
  ③ 冲突裁决（AI + 规则兜底）：合并/隔离/覆盖/人工介入，每次裁决写理由进事件流
  ④ 输出 preflight 报告 → 无冲突才允许 merge
```

**这是"人工 AI 同步中转站再分发"的规模化自动化版本。**

### 3.5 场景二当前落地差距（2026-08-07 核对，基于 2.5.6 源码）

> 本节记录「场景二」设计意图与 Sovei 当前真实能力的差距，作为待开发清单。

| 设计意图 | 当前落地 | 差距 |
|---|---|---|
| 多工作区（同项目多处 checkout） | ✅ 已实现：`workspace register/list/sync/promote/unregister`（`config/workspace.ts`） | 无 |
| 单一 hub 星型（hub 持稳定知识，satellite 持本地 feature 状态） | ✅ 已实现：首个注册为 hub；`sync` 仅推送 hub 的 stable 知识；`promote` 推送 satellite 候选 | 无 |
| Feature/spec 状态不共享 | ✅ 已实现：`sync` 只同步 knowledge/redlines，不同步 `specs/` | 无 |
| 知识冲突检查 | ⚠️ 部分：`sync`/`promote` 有**知识 id 冲突检测**（`Knowledge ID conflict`） | 仅限知识条目 id 级冲突，**非语义冲突** |
| **merge preflight（合并前语义冲突预检）** | ❌ 未实现 | **无 `merge preflight` 命令/机制**：不检测「同一业务域相反红线」「同一代码表面 coverage 改法矛盾」「两分支知识/决策矛盾」 |
| **联邦星型（每主干一个对账中枢）** | ❌ 未实现 | **当前是单 hub**：无 feature→test 中枢→master 中枢→全局的多级拓扑 |
| **红线 branch 作用域隔离** | ❌ 未实现 | `redlines.json` 的 `scope`/`owner` 仅是可选的审计描述字段，**非「按 branch 生效 + 作用域过滤」语义**；`sync` 目前会把 hub 全部红线推到 satellite，无工程专属隔离 |

**结论**：场景二已具备「单 hub 星型 + 知识同步」的雏形，但设计核心——**merge preflight 语义冲突预检、联邦星型、红线分支作用域隔离**——三项均未落地，是场景二未开发的主体。

## 4. 执行纪律链（两场景的灵魂）

### 4.1 诊断：四类执行错误

用户确认四种错误都见过，证明是系统性叠加，非偶发：

| 类型 | 表现 | 环节 |
|---|---|---|
| 类型3 基线污染 | 旧 spec 带偏，做过渡态却按完整新模块走 | 进上下文 |
| 类型2 理解偏 | 方向对但细节偏，无对照 | AI 理解 |
| 类型1 无清单执行 | 凭印象做，缺漏规则 | AI 执行 |
| 类型4 无卡点确认 | 自认做对，不再核对就交付 | 交付自检 |

**统一本质**：一条链（进上下文 → 理解 → 执行 → 交付自检）四环同时失守，单一机制救不了。

### 4.2 四个强制卡点

```
任务开始
  → ① 基线隔离：上下文只装"当前生效基线"，旧 spec/未来 spec 物理不进入
  → ② 判定样例：每条关键规则配"通过/不通过"样例，钉死"对"的形状
  → ③ 规则清单：规则从描述变为可逐条勾选清单，逐项落实
  → ④ 自检门：强制输出"我做了什么 + 逐条对照清单结果"，全过才交付
任何一步不通过即停下，不进入下一步。
```

### 4.3 为什么 Speckit/OpenSpec 救不了

它们擅长"把一个 spec 写清楚"，但假设需求是向前的、累积的。不处理：
- 需求在交付当天被**撕裂成过渡态 + 终态**并存（有退行的增量）。
- **AI 执行不跑偏的纪律**（上下文装配 + 执行自检）。

这正是自建 CLI 的差异化价值——被敏捷上线当天改需求的痛苦逼出来的执行层能力。

## 5. 落地优先级

### 5.1 原设计优先级（尚未落地部分）

1. **执行纪律链**（四个卡点）——最直接缓解"规则清楚但 AI 出错"，同时支撑两场景。
2. **基线隔离 + 判定样例**——解决场景二真实案例的"过渡态 vs 终态"基线失焦。
3. **联邦星型 + merge preflight**——规模化多分支协作。
4. **红线 scope/owner/branch 隔离**——解决"工程红线不同"。
5. **spec 分层 git 策略 + CLI 自动沉淀**——场景一。

### 5.2 基于当前落地差距的待开发排期（2026-08-07）

> 把 2.5/3.5 的差距映射为开发优先级。P0 影响当前使用正确性/协作，P1 消重复维护，P2 低风险顺带。

| 优先级 | 待开发项 | 对应场景 | 说明 |
|---|---|---|---|
| **P0** | merge preflight 语义冲突预检 | 场景二 | 设计核心，未落地。在现有 `workspace` 上加语义冲突检测（红线/coverage/知识矛盾），输出 preflight 报告 |
| **P0** | 红线 branch 作用域隔离 | 场景二 | 解决"工程专属红线不能强加其他工程"。给 `redlines.json` 的 scope 加分支语义 + 作用域过滤 |
| **P1** | Feature 收敛后主动归档 + spec 分层 git 策略固化 | 场景一 | learn/sync 收敛时主动归档过程产物，把四层 git 策略固化为模板/命令 |

| **P2** | 联邦星型（multi-hub） | 场景二 | 单 hub 已够个人用，规模化（多主干/多团队）时才需要多级对账中枢 |

## 6. 待确认问题

- "部分规则同步到旧模块"中"部分规则"是谁定、怎么定（影响是执行偏离还是语义裁剪）。
- 业务语义冲突检测的具体判定规则（需真实冲突案例定义）。
- 知识提取的"复用价值阈值"具体设计。
- **场景二先做 merge preflight 还是红线分支隔离**（个人多工程使用：红线隔离更急；规模化多分支合并：preflight 更急）——影响 P0 开发次序。
- **联邦星型是否本轮做**（当前单 hub 星型已满足个人 a/b/c 三工程；多级中枢需等到规模化场景真实出现）。
