# Sovei Engine 产品验证计划

**版本**：0.1  
**日期**：2026-08-18  
**目的**：在继续重构节点前，验证 Sovei 是否真正帮助用户完成需求，并确定下一轮开发边界。

## 1. 本轮规则

本轮先不新增节点、Skill、Adapter 或重大状态机重构。现有引擎作为待验证产品使用，所有问题先记录为产品观察、引擎缺陷或工程缺陷，不能立即凭感觉修复。

**验证隔离原则**：本轮不使用 Sovei CLI 作为主要验证入口，也不让 Sovei 自己生成、执行和裁判自己的验证流程。Sovei 是被测对象；外部验证者负责准备需求、观察过程、记录事实、执行独立测试并做最终评分。Sovei CLI 只能作为后续被测工具，在外部验证方案已经确定后被动运行。

每个场景都必须完整记录：

- 原始需求：不提前改写成技术语言；
- 用户目标：用户真正想得到的结果；
- 引擎判断：事实、风险、路由和下一步；
- 用户修正：引擎哪里理解错了或问得不好；
- 执行结果：代码 diff、测试和实际旅程；
- 负担：等待、重复填写、无效文档、重复扫描和不必要门禁；
- 结论：保留、修改、合并或删除哪个能力。

## 2. 三个验证场景

### S0：小修复

**示例需求**：修复一个明确的 CLI 错误提示，要求不改变命令行为。

**验证目标**：

- 引擎能否快速识别为低风险局部变更；
- 是否能进入 Quick 或轻量路径；
- 是否会强迫用户填写完整 Feature 文档；
- 是否能给出局部测试和 diff 证据；
- 越界时是否能升级到正式 Feature。

**通过标准**：用户能在一次短流程内确认范围、完成修改并得到验证结果；引擎没有要求与任务无关的长链路产物。

### S1：普通 Feature

**示例需求**：为 Sovei 增加 `clarify answer`，支持保存用户部分回答并重新评估路由。

**验证目标**：

- Explore 是否能理解产品目标而不直接跳到代码方案；
- Clarify 的信息缺口、问题、答案和路由是否可持久化；
- 12 阶段是否真的减少遗漏；
- 每个阶段是否改变了决策质量；
- 新会话能否根据状态恢复唯一下一步。

**通过标准**：从需求到验证的全过程可恢复、可审计；每个保留阶段都有明确价值证据。

### S2：跨模块长周期需求

**示例需求**：将 Workflow v3 状态核心接入新 Feature 的 `bootstrap/status/prepare/complete`，同时处理原子写、revision/CAS、旧 Feature 边界和回归测试。

**验证目标**：

- Wayfind 是否发现未决策项；
- Scope 是否覆盖状态、CLI、存储、测试和兼容边界；
- Converge 是否发现 Spec、Plan、Tasks 与实现的缺口；
- Verify 是否能分别证明需求正确和工程质量正确；
- 多次会话后是否仍能恢复上下文。

**通过标准**：关键影响面、风险、验收条件和未完成项均有证据，且没有静默跳过或伪完成。

## 3. 外部验证流程

### 3.1 验证角色分离

| 角色 | 负责什么 | 是否使用 Sovei 结论 |
|---|---|---|
| 产品观察者 | 定义用户目标、判断问题是否被解决、记录负担 | 否，独立判断 |
| 技术观察者 | 检查代码、测试、状态和运行证据 | 否，使用独立命令/工具 |
| 被测引擎 | 输出需求理解、问题、路由、阶段产物和实现结果 | 只能提供证据，不能自证 |
| 最终裁判 | 汇总产品和技术证据，决定保留/修改/删除 | 不由被测 CLI 担任 |

同一个人可以承担多个外部角色，但必须把“引擎输出”和“外部判断”分开记录。

### 3.2 每个场景的执行步骤

```text
1. 外部验证者保存原始需求和预期结果
2. 外部验证者先写出独立验收标准，不看引擎建议
3. 让被测引擎处理需求，保存原始输出
4. 外部验证者记录引擎事实、问题、路由和遗漏
5. 不在中途修改引擎，不让引擎自我修复
6. 外部验证者独立检查代码 diff、测试、文件状态和用户旅程
7. 外部验证者对照独立验收标准评分
8. 将引擎输出与外部判断做差异分析
9. 三个场景全部结束后，才决定是否重构
```

### 3.3 第一轮不依赖 Sovei CLI

第一轮验证可以使用通用方式完成：

- 用普通对话或独立 Agent 处理三类需求；
- 用人工维护的 Markdown 表格记录输入、输出和判断；
- 用 `git diff`、文件检查、独立测试命令验证实现；
- 用外部测试脚本或 Node 内置测试验证行为；
- 用第二个独立会话复核需求是否满足；
- 用人工产品判断评估流程是否增加负担。

Sovei CLI 不是本轮验证的裁判。即使使用 CLI 产生阶段产物，也只能把它当成被测输出，不能用它自己的 `status`、`verify` 或完成标记证明产品正确。

### 3.4 独立验收模板

验证开始前，外部验证者先填写：

```text
用户目标：
用户不接受的结果：
最小可交付结果：
必须验证的行为：
允许修改范围：
禁止修改范围：
预期风险：
独立验收命令/操作：
```

完成后再填写：

```text

与目标的差异：
引擎遗漏：
引擎误报：
引擎制造的额外负担：
独立证据：
产品结论：
技术结论：
```

## 5. 正确性评分

每项按 0、1、2 评分：0=失败，1=部分满足，2=满足。

| 维度 | 判断问题 | S0 | S1 | S2 |
|---|---|---:|---:|---:|
| 事实正确 | 引擎引用的项目、模块、状态和约束是否真实 | | | |
| 需求理解 | 是否理解用户目标，而不是只复述技术方案 | | | |
| 路由正确 | 是否进入适合的路径，是否避免过重或过快 | | | |
| 澄清质量 | 信息不足时问题是否具体、必要、可回答 | | | |
| 影响面完整 | 是否发现关键入口、消费者、契约和验证面 | | | |
| 执行纪律 | 是否按确认范围实施，没有越界或跳阶段 | | | |
| 验证质量 | 是否有足够证据证明目标和工程质量 | | | |
| 可恢复性 | 新会话是否能恢复并给出唯一下一步 | | | |
| 用户负担 | 流程是否减少而不是增加无效工作 | | | |

## 6. 结果决策门

三个场景完成后按以下规则决策：

- 任一场景在“事实正确、路由正确、执行纪律、验证质量”任一项为 0：先修对应基础能力，不扩展高级功能。
- S0 得分低：先修路由和 Quick/Clarify，不继续增加正式阶段。
- S1 得分低：先修状态源、阶段契约和恢复能力，不做 split 扩展。
- S2 得分低：先修 Scope、Wayfind、Converge 或 Verify 的证据链，不做 Graph Coding。
- 三个场景均无 0，且用户负担没有明显增加：才进入下一轮功能开发。
- 只有真实场景重复证明某个能力缺失，才把它固化为节点、状态字段或 Skill。

## 7. 本轮结束定义

本轮完成不代表引擎所有功能完成，而是完成一次产品判断。最终必须得到：

1. 三份场景记录；
2. 一份能力保留/修改/合并/删除清单；
3. 一份按证据排序的下一轮产品需求评估结果；
4. 一份明确的 MVP 完成标准；
5. 对 `specs/003-new-feature-workflow-state/` 是否继续实施的决定。
