# AI 开发面临的核心问题

> 日期：2026-07-15
> 来源：团队深度使用 AI 编程后的实战反思
> 状态：持续更新

---

## 一、信任链断裂（最致命）

### 问题

传统开发的信任链是完整的：人写代码 → 人懂代码 → 人能改代码。

AI 深度介入后信任链断裂：

```
传统：  人写代码 → 人懂代码 → 人能改代码 → 信任链完整
AI：    AI 写代码 → 人"审查"代码 → 人不懂代码 → 人改不动 → 信任链断裂
```

### 具体表现

1. **开发者改不动代码了** — AI 生成 800 行代码，开发者审查时大脑在做"模式匹配"而非"逐行理解"。看着像对的就过了。3 个月后 Bug 出现，打开代码发现自己看不懂审查过的代码。
2. **代码审查变成仪式感** — 审查者只在表面验证，不做深度理解。"代码审查"从质量保证退化成了流程仪式。
3. **代码从黑盒变白盒（伪装的）** — 实际是"伪装成白盒的黑盒"。所有人以为审查过了所以可控，但实际上没有人真正理解代码的业务意图。Bug 爆发时没人能快速定位。

### 根因

AI 写的代码风格、命名、抽象层次和人类不一样。人类审查 AI 代码时的假设是"Reviewer 能看懂代码"，这个假设在 AI 全量生成代码后不成立了。

## 二、AI 幻觉因子（静默漂移）

### 问题

AI 的幻觉不是"突然说胡话"，而是**静默漂移**：每次偏差都很小，人审查时看不出来，累积起来很致命。

### 漂移过程

```
第 1 次：AI 按业务写代码 → 正确
第 2 次：AI 按业务写代码 → 大部分正确，小地方用了自己的判断
第 3 次：AI 基于"自己的判断"继续写 → 开始偏离业务
第 5 次：AI 完全按"它认为合理"的方式写 → 业务逻辑已经偏了
```

### 漂移特征

- **每次偏差都很小**，人审查时看不出来
- **累积起来很致命**，最终代码和业务意图完全脱节
- **AI 自己不知道在漂**，它每次都觉得自己在"正确实现"
- **开发者也不知道**，因为开发者已经不读代码了

### 真实案例

inpaint 参数链路坑：AI 在"再次生成"时不传 description，因为 AI 觉得"description 是可选的"——但业务上 description 暴露了系统提示词。AI 不知道这是业务红线，它只是在做"合理的技术决策"。

## 三、知识不沉淀（团队维度）

### 问题

团队成员各自用 AI 开发，踩过的坑、做过的决策、业务约束都散落在个人记忆或对话历史里。其他人遇到类似问题时无法检索到这些经验。

### 具体表现

1. **开发者 A 踩了坑 → 开发者 B 重复踩** — 没有 knowledge 共享机制
2. **开发者 A 做了技术决策 → 开发者 B 不知道 → AI "优化"掉了有意的决策**
3. **AI 写代码时拿不到业务上下文 → 在真空中写代码 → 技术可能对，业务一定偏**
4. **对话历史不可复现** — 10 轮对话里的需求散落各处，AI 换个会话就忘了

### 根因

没有统一的知识系统来存储、检索、约束 AI 的行为。代码审查已经不可靠了（人看不懂 AI 代码），单元测试也不够（测试也可能被 AI 写偏），**唯一可靠的是：AI 写代码前，先拿到业务约束**。

---

## 四、现有方案的局限

### 行业开源框架都不够

| 框架 | 解决了什么 | 没解决什么 |
|------|-----------|-----------|
| Spec-Kit (GitHub) | spec→plan→tasks 流程 | 无知识沉淀、无跨项目、无角色分工 |
| OpenSpec (Fission AI) | 棕地变更可审计 | 无知识沉淀、依赖开发者自律 |
| BMAD-METHOD | 12+ Agent 角色协作 | 无知识沉淀、学习曲线陡 |
| Kiro (AWS) | hooks 自动化 | 闭源、数据合规风险、无知识沉淀 |
| CoStrict (深信服) | 自动学习业务知识 | 偏安全审计、无 spec 工作流 |

### 关键发现

**没有任何开源框架同时解决"AI 漂移 + 知识沉淀"两个问题。**

所有框架都在解决"怎么让 AI 按 spec 写代码"，但没有一个在解决"AI 写完代码后，怎么把业务知识沉淀下来防止下次漂移"。

---

## 五、解法方向：知识系统 = AI 的业务护栏

### 核心原则

> 当开发者不能靠"读代码"保证正确性时，知识系统成为唯一业务锚点。

### 审查方式转变

| 维度 | 传统审查 | 有知识锚点后 |
|------|---------|------------|
| 审查什么 | 代码逻辑 | spec 对齐（AI 是否遵守了业务约束） |
| 审查方式 | 逐行读代码 | 对比 AI 产出 vs 业务地图的红线/参数链路 |
| 审查能力要求 | 必须懂代码 | 懂业务即可 |
| 拦截 AI 漂移 | 靠人眼（不可靠） | 靠知识约束 + CI 门禁 |

### 三层架构

```
本地 Harness（管真相）
  ↓ 精选上架
ima 知识库（管召回 / AI 的业务护栏）
  ↓ 约束
AI 写代码（在约束范围内）
```

### 业务地图模板（每功能一份）

每个业务功能沉淀一份业务地图，上架到 ima，包含 5 个 section：

1. **业务意图** — 为什么存在，解决什么问题
2. **业务红线** — AI 绝对不能违反的约束，每条配"违反后果"
3. **参数链路** — 输入→中间→提交→回填完整链路，AI 不能自作主张改
4. **已知坑点** — 踩过的坑 + 解决方案，标 resolved/unresolved
5. **关键决策（ADR 引用）** — 为什么这么做，AI 看到后不会"优化"掉有意的决策

### 工作流

```
项目 A/B/C 新增经验
  → 合并到 E:\memory（Harness 中枢）
  → 去重、重编号、过滤
  → 生成 ima-export 摘要
  → 上传/同步到 ima 知识库
  → 对话时 AI 优先检索 ima
  → 需要落地修改时回到本地文件
```

## 六、Harness 需要补强的 3 个能力

| 优先级 | 能力 | 说明 |
|--------|------|------|
| P0 | 语义检索层 | ima-export 精选上架，验证检索粒度 |
| P1 | 知识生命周期 | ADR 加 status 字段、坑点加 resolved 标记、定期归档 |
| P2 | 自动化校验 | sync-check 脚本，三方 hash 对比 + BOM/乱码检测 |

### 团队协作需补的 4 个维度

1. **分工协议** — Spec Owner / AI Operator / Reviewer / Knowledge Manager
2. **PR 关联** — tasks.md 状态和 PR 绑定，合并即关闭任务
3. **质量门禁** — CI 自动跑 lint / type-check / test / spec 一致性校验
4. **知识共享** — ima 层让团队成员检索到别人的 ADR/坑点/spec

## 七、可借鉴的开源方案

| 来源 | 借鉴什么 |
|------|---------|
| BMAD-METHOD | 12+ Agent 角色分工模型 |
| Spec-Kit | phase-gated 阶段门禁 |
| Kiro | hooks 自动化触发 |
| CoStrict | 自动学习历史代码和业务知识（半自动化业务地图） |

**保留自己的**：跨项目同步 + 分发保护 + 知识沉淀 + ima 语义检索（这些是没有任何开源框架能给的）。
