# 面试准备：我的 AI 辅助开发解决了什么

> 场景：面试官问"你的 AI 辅助开发解决了什么"，公司想做一个自我迭代编排的 Agent 服务于开发。
> 核心叙事：**他们想解决的痛点，我已经解决了，而且成本远低。**

---

## 一、30 秒电梯回答

> 我深度使用 AI 编程后，发现了三个致命问题：信任链断裂、AI 静默漂移、知识不沉淀。我做的方案直接解决了这三个问题——用结构化知识库在 AI 写代码前就给约束，把验证从"逐行读代码"变成"对齐业务红线"。编排 Agent 想解决的本质上也是这几个问题，但走的是"事后验证"路线，成本高且会碰到元问题递归。我的方案是"事前约束"，已经跑通了，成本极低。

---

## 二、完整回答（3-5 分钟）

### 第一步：我的 AI 辅助开发解决了什么（讲痛点 + 讲解法）

我深度使用 AI 编程后，发现 AI 写代码有三个致命问题，我的方案逐个解决了它们。

#### 痛点一：信任链断裂

```
传统：  人写代码 → 人懂代码 → 人能改代码 → 信任链完整
AI：    AI 写代码 → 人"审查"代码 → 人不懂代码 → 人改不动 → 信任链断裂
```

AI 生成 800 行代码，开发者审查时大脑在做"模式匹配"而非"逐行理解"。看着像对的就过了。3 个月后 Bug 出现，打开代码发现自己看不懂审查过的代码。代码审查从质量保证退化成了流程仪式。

**我怎么解决的**：不靠人读代码保证正确性，靠**业务约束锚点**。AI 写代码前先读业务地图（业务红线 + 参数链路 + 已知坑点），人只需要验证"AI 是否遵守了红线"，不需要逐行读代码。验证能力要求从"必须懂代码"降到"懂业务即可"。

#### 痛点二：AI 静默漂移

AI 的幻觉不是"突然说胡话"，而是**静默漂移**：每次偏差都很小，人审查时看不出来，累积起来很致命。

```
第 1 次：AI 按业务写代码 → 正确
第 2 次：AI 按业务写代码 → 大部分正确，小地方用了自己的判断
第 3 次：AI 基于"自己的判断"继续写 → 开始偏离业务
第 5 次：AI 完全按"它认为合理"的方式写 → 业务逻辑已经偏了
```

> 真实案例：局部修改功能，AI 在"再次生成"时不传 description 参数，因为它觉得"可选参数不传也合理"。但业务上 description 暴露了系统提示词——这是业务红线。AI 不知道这是红线，它只是在做"合理的技术决策"。

**我怎么解决的**：每个业务功能沉淀一份业务地图，业务红线明确写出来，每条配"违反后果"。AI 写代码前先读，在红线范围内行动。**漂移被拦截在单次任务内，不会累积。**

#### 痛点三：知识不沉淀

团队成员各自用 AI 开发，踩过的坑、做过的决策、业务约束都散落在个人记忆或对话历史里。开发者 A 踩了坑，开发者 B 重复踩。AI 写代码时拿不到业务上下文，在真空中写代码——技术可能对，业务一定偏。

**我怎么解决的**：建了一套跨项目同步的知识库中枢：

| 层级 | 内容 | 作用 |
|------|------|------|
| 业务地图（每功能一份 MD） | 业务意图 + 业务红线 + 参数链路 + 已知坑点 + 关键决策 | AI 写代码前先读，在约束内行动 |
| 踩坑知识库 | 团队踩过的坑 + 解决方案 | AI 检索到后不重复踩 |
| 决策记录（ADR） | 为什么这么做 | AI 看到后不会"优化"掉有意的决策 |
| IDE 约束加载 | 三套 IDE 自动加载约束文件 | 开发者无感，AI 自动拿到业务上下文 |
| 同步分发 | 中枢更新 → 全量分发到所有项目 | 知识一处更新，处处生效 |

**知识复利效应**：坑踩一次，写进知识库，全团队全项目的 AI 都不会再踩。

---

### 第二步：编排 Agent 想解决的也是这些痛点，但路线不同

公司想做自我迭代编排的 Agent，本质上是想自动化跑完"需求→实现→验证→迭代"的闭环。它想解决的核心问题和我一样——**AI 产出不可靠 + 知识不沉淀**。

但编排 Agent 走的是**事后验证**路线：让 Agent 先跑，跑完再验证准确率、检测偏移量。这条路有三个绕不开的难题，而**这些恰好是我已经解决的**：

#### 他们的痛点一：验证准确率需要 ground truth——我已绕过

编排 Agent 需要衡量"Agent 做对了没有"，这需要一个"正确答案"。但业务需求的正确性没有自动化判断标准——单元测试可能被 AI 写偏，代码审查者已在做模式匹配。**最终还是要人介入判断，等于没有减少人的负担。**

> **我的方案怎么绕过的**：不做事后验证，做事前约束。AI 写代码前就拿到业务红线，在约束范围内行动。验证从"判断 AI 产出对不对"变成"AI 有没有碰红线"——后者成本极低，10 分钟搞定，且可靠。

#### 他们的痛点二：偏移检测是元问题递归——我已拦截

编排 Agent 自身也会静默漂移——它基于自己的判断继续迭代，偏离业务意图。那需要一个"元 Agent"来检测偏移。但元 Agent 本身也会漂。**谁来检测元 Agent？无限递归。**

> **我的方案怎么拦截的**：每次 AI 产出都有人审红线，漂移被拦截在单次任务内，根本不会累积到需要"检测"的程度。不需要元 Agent，不需要偏移检测算法，一个 MD 文档就够了。

#### 他们的痛点三：知识沉淀——我已跑通

编排 Agent 的知识散落在对话日志和运行记录里，不可检索、不可复用。

> **我的方案已经跑通的**：结构化 MD 知识库，跨项目同步分发，AI 自动检索。坑踩一次全团队免疫，决策记一次 AI 不再"优化"掉。这是显性资产，不是黑盒日志。

---

### 第三步：我的方案亮点

| 亮点 | 说明 |
|------|------|
| **事前约束 > 事后验证** | 成本低一个数量级。约束是 AI 写代码前给的，验证是写完后做的——前者防止问题发生，后者在问题发生后找问题 |
| **验证门槛降到"懂业务"** | 不需要逐行读代码，只需要对齐 5 条业务红线。审查时间从 30+ 分钟降到 10 分钟，且可靠 |
| **知识复利** | 每踩一个坑，写进知识库，全团队全项目的 AI 永久免疫。编排 Agent 做不到这个，因为它的知识不可检索 |
| **漂移拦截在单次任务内** | 不需要偏移检测算法，不需要元 Agent，人审红线就是最好的漂移拦截器 |
| **1-2 周见效，可增量上线** | 选一个核心功能写业务地图，立刻提效。不需要等整个系统跑通 |
| **已验证可行** | 跨 3 个项目同步运行，三套 IDE 自动加载，弱模型也能适配 |
| **是编排 Agent 的前置条件，不是替代品** | 积累足够的业务地图和坑点数据后，可以直接喂给编排 Agent 作为约束层。先有护栏，再谈自动驾驶 |

## 三、可能被追问的问题

### Q1：你的方案不就是写文档吗？

> 不是写文档，是**改变 AI 写代码的前置条件**。传统文档是给人看的，我的约束文档是给 AI 看的——它决定了 AI 在什么范围内行动。
>
> 关键区别在于结构化：按"业务红线（带违反后果）+ 参数链路 + 已知坑点"组织，让 AI 能精确检索到、能判断哪些不能碰。本质上是把"人的业务知识"变成"AI 的行为护栏"。

### Q2：编排 Agent 也能加约束啊，有什么区别？

> 区别在于**约束生效的时机和成本**。
>
> 编排 Agent 的约束是在"事后验证"环节——Agent 已经跑完了一轮，你再检查它有没有偏。这需要构建验证系统、偏移检测，成本极高。
>
> 我的约束是在"事前"——AI 写代码前就拿到了，根本不会碰红线。不需要验证系统，不需要偏移检测。一个 MD 文档解决问题。
>
> 而且，编排 Agent 最终也需要这样的知识库作为约束层。**我做的事情是编排 Agent 的地基。**

### Q3：你怎么保证约束文档不过期？

> 三个机制：
> 1. **生命周期标记**——坑点标 resolved/unresolved，决策标 status
> 2. **随 PR 更新**——每次改功能时顺手更新对应业务地图，不额外增加流程
> 3. **同步分发**——中枢更新后自动分发到所有项目实例
>
> 关键对比：文档过期的风险是**显性的**——你打开文档就知道它过没过期。而 Agent 的漂移是**隐性的**，你根本不知道它什么时候开始偏的。显性风险可控，隐性风险致命。

### Q4：你有量化数据吗？

> 审查时间从"逐行读 800 行代码（30+ 分钟，且不可靠）"降到"对齐 5 条业务红线（10 分钟，且可靠）"。
>
> 知识复利：一个参数链路的坑（description 漏传导致系统提示词泄露），写进知识库后，后续所有涉及该功能的 AI 生成都自动带上了这个参数——**同样的坑没有第二次出现**。
>
> 跨项目复用：踩坑记录、决策记录一处更新，3 个项目同时生效。

### Q5：如果给你足够的资源，你会做编排 Agent 吗？

> 会，但会基于我现有的知识库来做。把积累的业务地图和坑点数据喂给编排 Agent 作为约束层。
>
> **先有护栏，再谈自动驾驶。没有护栏的自动驾驶就是赌博。我的知识库就是那个护栏。**

## 四、一句话收尾

> **编排 Agent 是"先造车再修路"，我的方案是"先修路"。路就是知识库和业务约束——成本极低，但已经解决了信任链断裂、AI 漂移、知识不沉淀这三个核心问题。将来要上编排 Agent，这条路直接就能用。**
