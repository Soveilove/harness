## P0-2 Merge Preflight 语义冲突预检已实现

- 新增 `packages/sovei-core/src/preflight/` 模块：`types.ts`（冲突类型/裁决/报告结构）、`checker.ts`（`MergePreflightChecker` 核心检测器 + `renderPreflightReport` Markdown 渲染）、`index.ts`（barrel export）。
- 三类语义冲突检测：
  1. **红线冲突**：同一 redline ID 规则不同→blocking；执行级别不同→blocking；active/inactive 差异→warning。
  2. **知识冲突**：同一 ID content 不同→blocking；同类型同标题不同 ID 不同内容（语义冲突）→warning；lifecycle 差异→warning。
  3. **coverage 冲突**：同一代码表面在 coverage-matrix.md 中变更意图不同→warning（解析表格行和列表行）。
- 冲突裁决：`resolveConflict()` 支持 merge/isolate/override/manual 四种动作，裁决后重新评估 `canMerge`（blocking 且非 manual 裁决解除后可合并）。

- CLI 命令：`sovei workspace preflight <source> <target>`，选项 `--feature <path>`（可重复，指定 coverage-matrix 检查路径）、`--report <file>`（输出 Markdown 报告文件）。

### 子 Agent 强化方向（§2.9，架构观察）
思考 Sovei 工作流中哪些串行 I/O 密集型节点可用子 Agent（sub-agent）并行化：

1. **SA-1 cross-feature 相关性过滤**（P1）：`--cross-feature` 串行遍历所有 Feature 目录读 decision-log，50+ Feature 时瓶颈明显。子 Agent 并行读取 → 各自输出摘要 + 相关性评分 → 主 Agent 取 Top-N。直接解决 P1-3 上下文包膨胀。**优先实施**。
2. **SA-2 context build 组装**（P2）：required 项（红线+知识+规范+产物）串行加载。子 Agent 分组并行加载，主 Agent 合并 + 优先级截断。
3. **SA-3 converge/verify 代码审查**（P2）：单一 Agent 会话做全部审查。子 Agent 分维度并行（类型安全/测试覆盖/规则合规/架构合规），主 Agent 汇总裁决。
4. **SA-4 drift detection 影响面评估**（P1，与 drift MVP 同期）：未实现。子 Agent 按规则类别并行扫描（红线 scope/coverage-matrix/knowledge 证据），主 Agent 汇总 drift 报告。
5. **SA-5 preflight 三类冲突检测**（P2）：当前串行执行红线→知识→coverage，三类互相独立可并行。当前数据量小收益有限，规模化后可提升。
6. **SA-6 learn 知识提取**（P2）：串行解析→匹配→创建/晋级。子 Agent 并行（提取新观察/搜索匹配/评估蒸馏价值），知识库写入仍需串行保一致性。

**设计约束**：子 Agent 强化是宿主 AI 层面的并行编排，不是 Sovei CLI 自身并发改造。需定义子 Agent 契约（输入 JSON + 输出 JSON），类似 `sovei quick --json` 的模式。

## quick 通道「过度防御 + 冷启动」缺陷分析（2026-08-10）已入 DEV_BACKLOG §3.7.1 / P2-7

- **用户实际场景**：`sovei quick "..." --paths <file>` 返回 `git: null` + escalated + 「人工介入：目标范围或上下文相关性仍不确定」。用户误判为「无 commit 导致」，实际根因更深。
- **根因（核实 run.ts + policy.ts）**：
  - `run.ts` L148-151 `needsEscalation`：`!target || status==='escalated' || status==='expanded' || declaredPaths.length!==1` 任一满足即 escalated——5 个条件都是「不确定就拒绝」，正常路径极窄。
  - `policy.ts` L177：`uncertain = 有 paths 且有未命中的红线/规则候选` → `status='expanded'` → 触发 escalated。本次实际触发点就是 `status='expanded'`。
  - **`git: null` 是 escalated 分支 early-return 的返回值（run.ts L161），根本没走到 git 验证**。用户以为「无 commit 导致」是误解；真到 git 验证时无 commit 返回的是 `baseline-unreadable`。
  - 冷启动（无 commit）是次要因素，且无「建议先建基线 commit」引导。
- **判断：不是「为了开发而开发」**——机器先审 + git 范围验证有真实治理价值（解决问题二），但「任何不确定都 escalated」的判定策略过度防御，与「快速」初衷矛盾。
- **建议改进（已入 §3.7.1）**：P1 区分「可安全降级与必须人工」——`status='expanded'` 降级为警告先做 git 验证；P2 冷启动引导 + 放宽 declaredPaths（允许 0/多路径）。与 P2-5（--paths 语义修正）协同。
- **DEV_BACKLOG 落位**：§1 未完成项表加 P2-7 行；§3.7 表格加 P2-7 行 + 新增 §3.7.1 详情节；§8 开发顺序加步骤 6.6；§9 待人工决策加 ❓ 项（判断依据：quick 使用频率）。
