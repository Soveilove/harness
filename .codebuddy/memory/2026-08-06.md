# 2026-08-06

## Sovei CLI 两个核心场景的架构分析（与用户讨论）

用户提出两个待解决场景，并澄清了第一个场景的真实含义（指本项目 `d:/project/harness` 自身，而非通用用户项目）：

### 场景 1：本项目自身的 spec/工作流文件是否进 git
- 澄清：用户问的是 Sovei CLI 项目 **自身**（不是通用用户项目）。它用 CLI 开发 AI，是活体实验品，spec/工作流文件就是自我迭代的语料，**必须保留**。
- 现状确认：`specs/` 下全部文件（含 `workflow-state.yaml`、`workflow-events.jsonl`、`wayfinder-events.jsonl`、`wayfinder.json`、`decision-tickets/*.json`、`history/revision-N/` 归档）都已被 git 跟踪；`.gitignore` 只排除 node_modules/dist/public-repo。
- 结论：**当前"全部进 git"是正确的最终形态**，不应改动。事件流(`workflow-events.jsonl`)是事实源，git 提供不可变历史基线。可选优化：`wayfinder.md`/`redlines.md` 等可重建派生视图可考虑 .gitignore，但对该项目而言保留也无害。

### 场景 2：多分支/多工程(A/B/C)的冲突问题
- 用户实际体验：并行三条线，弄了三个工程 a/b/c，发现需求冲突、代码变动冲突、业务红线不同。
- 现状：`packages/sovei-core/src/config/workspace.ts` 已有 hub/satellite 架构（`syncToSatellite` 推 stable 知识+红线、`promoteToHub` 晋升 candidate、knowledge ID 冲突检测）。`WorkspaceEntry.branch` 只是标签，无分支操作/合并/冲突解决。
- 空缺：
  - 需求冲突：只检测 knowledge ID 冲突，无 spec/scope 层需求重叠检测
  - 代码变动冲突：无跨工作区文件级冲突检测（靠 git merge 撞）
  - 业务红线冲突：`redlines.json` 是全局单例，红线无 owner/scope/branch，无法表达分支间红线差异
- 建议方案：给 redline/knowledge/Feature 增加 `scope`/`owner`/`branch` 字段（红线按分支生效，sync 做作用域过滤）；实现 `workspace preflight`（基于 coverage-matrix 跨工作区域重叠检测）；后期扩展 wayfinder claim 为跨工作区 claim。
- 落地优先级：场景1(纯配置.gitignore分层,低成本) → 场景2a(红线按分支作用域化+sync过滤) → 2b(preflight域重叠检测) → 2c(跨工作区claim)

### 设计关键点
- 两个场景本质是同一问题两面：时间维度(git历史) vs 空间维度(多工程)，都是"谁拥有事实源、跨边界如何同步"。核心资产(事件溯源+单一事实源+生命周期candidate/pending/stable)已正确，缺的是**作用域(scope/owner/branch)声明**。
- 通用用户项目建议忽略部分派生文件；本项目特殊，全部保留。

## 深入讨论后收敛的设计决策（已写入 design-docs/SOVEI_SCENARIOS_DECISION.md）

### 澄清场景一真实含义
- 用户最终澄清：场景一问的是**通用用户项目**使用 CLI 时 spec/工作流文件进不进 git（本项目是开发期，先不管）。
- 用户倾向：spec 不需要全进 git，"CLI 化自动沉淀"（AI 判断 + 规则边界）。用户认可"AI 自主 + 规则边界 + 理由审计"方向，反对纯 AI 自由判断（会摧毁事件溯源可复现性）。

### 场景一决策（四层分层）
- ①事实源(events/tickets)必须进git，规则锁定；②"为什么"(decision-log/reconciliation)必须进git；③知识沉淀(knowledge/*.json)必须进git，CLI提取candidate+人工promote；④过程产物(spec/plan/tasks细节)收敛后归档；派生视图(wayfinder.md/workflow-state.yaml)忽略。
- "CLI化自动沉淀"形态：spec→learn/sync自动提取(带理由+事件流)→knowledge candidate→人工promote→stable。防"spec膨胀变knowledge膨胀"需复用价值阈值+最少证据。

### 场景二决策（联邦星型 + merge preflight）
- 用户实际做法：人工让AI同步"中转站"再分发（个人星型拓扑），是中转站是cli化sop前身。
- 规模化(千千万万开发者+多分支合并test/master)后：纯星型有瓶颈，升级为**联邦星型**（每主干一个对账中枢，feature分支先合到所属主干中枢，主干间再合）。
- 三样东西处理：知识共享过中枢；红线部分共享(专属必须隔离，需加scope/owner/branch)；Feature状态不共享。
- 核心机制：**merge preflight**（合并前语义冲突预检：文本冲突git自带 + 业务语义冲突检查redlines/knowledge/coverage + AI裁决带理由 + 无冲突才merge）。

### 执行纪律链（两场景灵魂，解决"规则清楚但AI执行出错"）
- 用户真实案例：重构模块放test，产品上线当天说"新模块有风险不上，旧模块同步部分新模块规则"→需求撕裂，AI执行一直出错(缺漏/理解不了)，Speckit/OpenSpec都救不了。
- 诊断四类错误(用户确认都见过，系统性叠加非偶发)：①基线污染(进上下文) ②理解偏(理解) ③无清单执行(执行) ④无卡点确认(交付自检)。
- 四卡点机制：①基线隔离(上下文只装当前生效基线，旧/未来spec物理不进入) ②判定样例(每规则配通过/不通过样例钉死"对"的形状) ③规则清单(描述变可勾选清单逐项落实) ④自检门(强制输出"做了什么+逐条对照清单结果"，全过才交付)。
- Speckit/OpenSpec救不了的原因：假设需求向前累积，不处理"需求被撕裂成过渡态+终态并存(有退行增量)"和"AI执行不跑偏纪律"。这是自建CLI差异化价值。

### 用户偏好
- 用户多次强调"因为都是AI化的流程，这是我做的意义"，倾向让AI自己判断，但接受"AI判断+确定性边界+理由审计"而非纯AI自由。
- 用户要求多角度分析、不迎合。
- 设计权分配依据可逆性：毁系统的交规则；能改的交AI(带理由+事件流)；质量闸门交人工。

### 落地优先级（文档第五节）
1.执行纪律链(四卡点) → 2.基线隔离+判定样例(解决过渡态vs终态) → 3.联邦星型+merge preflight → 4.红线scope/owner/branch隔离 → 5.spec分层git策略+CLI自动沉淀

### 待确认

- 业务语义冲突检测的具体判定规则(需真实冲突案例定义)

## 待续：重大设计问题（用户将新开对话续聊）
用户发现：**改动需求时，业务拓扑(business-map)和业务红线(redlines)没跟着变动。**
- 分析：分两类。情况A(纯流程/工具改动如 rules 精炼)→拓扑/红线本就不该变，没变正确。情况B(真正业务需求改动)→若动了代码/改了业务约束，拓扑/红线该跟着变，没变是真问题。
- 根因判断：拓扑/红线只在 `onboard` 一次性扫描生成，后续需求/代码改动**没有机制触发重新评估**，所以"看起来没变"。
- 本质：与"需求撕裂后 AI 执行基线失焦"同根因——需求是时间变量，业务事实需跟随演进，但缺"需求改动→重新评估业务事实(拓扑/红线/spec)"的联动。
- 建议方向：引入"变更影响评估"(Impact Re-evaluation)——需求/代码改动时评估对拓扑/红线影响(哪些域动、拓扑要不要更新、红线增删改)，写进 change 记录，AI 基于最新事实判断。区别于 onboard 的一次性全量扫描。
- 用户尚未确认是情况A/B/C，需新对话继续。发布时用户明确说"先提交并发布，然后总结问题，重新开新对话继续聊"。
