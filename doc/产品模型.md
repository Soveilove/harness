# Sovei 产品模型

**版本**：0.1
**日期**：2026-08-18
**定位**：产品视角的统一理解，不替代 `design-docs/产品需求文档.md` 的详细需求。

## 1. 一句话定义

Sovei 是一个把“不完整或复杂的自然语言需求”带到“有证据的可验证交付”的 AI 开发工作流引擎。

它不首先解决“如何生成更多文档”，也不首先解决“如何增加更多命令”，而是帮助用户持续回答：

1. 我真正要解决什么问题？
2. 项目中已经确认了哪些事实？
3. 还缺哪些必须由用户决定的信息？
4. 当前应该走哪条路径？
5. 下一步是否合法？
6. 做完之后有什么独立证据？

## 2. 目标用户与核心任务

### 2.1 目标用户

- 同时维护多个项目、分支或 Agent 宿主的个人开发者；
- 需要跨会话继续工作的开发者；
- 既需要产品判断，又需要工程影响面和验证证据的技术负责人。

### 2.2 用户真正购买的结果

用户不是为了得到一套阶段文件，而是为了降低以下风险：

- 做错需求；
- 漏改入口或消费者；
- 在信息不足时过早实现；
- 多次会话后丢失上下文；
- 以为完成但没有证据；
- 简单任务被重流程拖慢；
- 复杂任务因缺少边界而失控。

## 3. 核心产品闭环

```text
自然语言需求
  → Explore：理解需求、扫描事实、识别风险
  → Clarify：提出必要问题，保存部分回答
  → Reassess：根据新信息重新评估
  → 路由：Quick / 正式 Feature / split-candidate / blocked / cancelled
  → 执行：在已确认范围内推进
  → 验证：用独立证据证明用户目标和工程质量
  → 学习：沉淀有证据且有复用价值的知识
```

产品成功的最小表现是：用户每次回来都能看到**当前目标、已知事实、未决问题、风险、唯一下一步**。

## 4. 产品能力分层

| 层 | 用户问题 | 当前定位 | 当前动作 |
|---|---|---|---|
| 需求进入 | 我应该从哪里开始？ | Explore 是统一入口的设计方向 | 优先验证真实旅程 |
| 需求澄清 | 信息不全怎么办？ | PRD 已定义 clarification-pack 和多轮回答 | 作为 MVP 核心验证 |
| 路由 | 这个需求该走快路径还是正式流程？ | Quick 尚未被 Explore 可靠控制 | 先定义准入和升级规则 |
| 状态恢复 | 下次回来怎么继续？ | v3 JSON 状态核心是工程基础 | 先稳定唯一事实源 |
| 影响分析 | 会影响哪些模块和约束？ | Wayfind、scope、架构扫描已有部分能力 | 用 S2 场景验证是否真实有用 |
| 执行治理 | 怎么避免越界和伪完成？ | 阶段门禁、任务、converge/verify 已有基础 | 只保留能改变决策质量的门禁 |
| 交付证明 | 怎么知道真的完成？ | 测试、证据、verify 有基础 | 要求独立验收，不接受自证 |
| 知识复用 | 经验如何避免污染？ | candidate → pending → stable 已有基础 | 后续补价值阈值 |
| 扩展生态 | Skill 和 Agent 如何接入？ | 已有适配器和 Skill 运行时 | 暂不作为主线 |

## 5. 正式 Feature 的用户语言解释

12 阶段不是 12 个必须填写的表格，而是 12 类风险检查：

| 阶段 | 用户能得到的价值 | 如果没有价值就不应保留为重门禁 |
|---|---|---|
| `explore` | 知道需求和项目现状 | 不能只是生成探索文档 |
| `grill` | 发现产品决策和取舍 | 不能重复询问已知事实 |
| `wayfind` | 找到影响面和依赖 | 不能只罗列目录 |
| `spec` | 明确用户故事和验收 | 不能直接变成技术实现方案 |
| `scope` | 确认允许/禁止范围 | 必须能阻止越界 |
| `plan` | 形成可执行方案 | 必须说明为何这样做 |
| `tasks` | 拆成可验证工作 | 必须能用于执行和追踪 |
| `implement` | 在确认范围内修改 | 不得静默扩大范围 |
| `converge` | 找出计划、实现和证据缺口 | 不能只是再次总结 |
| `verify` | 独立证明需求和质量 | 不能只读自己的完成标记 |
| `learn` | 提炼可复用经验 | 只有有证据、有复用价值才入库 |
| `sync` | 让项目和知识保持一致 | 不能把旧事实重新写回当前状态 |

## 6. 第一阶段 MVP

第一阶段只证明以下闭环，不扩展高级能力：

1. 一个不完整需求能够进入澄清；
2. 引擎能说明缺什么、为什么缺、如何回答；
3. 用户可以分批回答，已答和未答内容不会丢失；
4. 回答后重新评估并给出唯一下一步；
5. 小修复不会被完整流程压垮；
6. 普通 Feature 能恢复、执行并验证；
7. 跨模块需求能暴露影响面和未决策项；
8. 新会话可以根据结构化状态继续；
9. 所有失败都能区分为需求、环境、权限、引擎、决策或实现问题。

## 7. 明确暂不做

在 MVP 证据完成前，不启动：

- Graph Coding / 统一关系模型；
- MCP Server；
- 联邦多 Hub；
- 外部 Skill 自动升级；
- Cursor Adapter；
- 全量语言扫描；
- 为旧 Feature 做迁移或兼容；
- 为了让旧测试全绿而恢复旧状态 fallback。

## 8. 产品判断标准

Sovei 正确，不等于测试数量多或阶段全部完成。必须同时满足：

| 维度 | 通过问题 |
|---|---|
| 事实正确 | 引擎说的项目、文件、状态和约束是否真实？ |
| 需求理解 | 是否理解用户目标，而不是只复述技术词？ |
| 路由正确 | 简单任务没有过重，复杂任务没有过快？ |
| 执行正确 | 是否按确认范围实施，是否避免静默跳阶段？ |
| 交付正确 | 用户目标是否满足，证据是否足够？ |
| 用户负担 | 是否减少了重复劳动和不必要文档？ |

## 9. 产品结论

当前方向是对的，但不能继续用“增加节点或修旧测试”代替产品验证。开发主线应围绕一个问题收敛：

> Sovei 是否能让用户在不确定时更有把握，在复杂时不遗漏，在完成时有证据？

任何新增功能都必须先回答：它解决哪一个已复现的用户问题，如何通过独立场景验证，以及失败时是否应删除或合并。
