# Sovei 产品驱动开发路线

**版本**：0.1
**日期**：2026-08-18
**依据**：`design-docs/产品需求文档.md`、`design-docs/产品验证计划.md`、`design-docs/产品功能需求.md`

## 1. 开发总原则

开发不再从“下一个技术模块是什么”开始，而从“哪个用户问题已被观察到”开始。

每个需求必须具备：

- 用户目标；
- 不接受的结果；
- 最小可交付结果；
- 允许和禁止修改范围；
- 独立验收方式；
- 明确的删除、合并或保留条件。

一次只开发一个产品问题。未完成验证前，不并行启动新的主线。

## 2. 当前阶段：产品验证，而不是功能扩张

当前先不增加节点、Skill、Adapter 或高级状态能力。使用三个真实任务验证产品价值：

| 场景 | 验证问题 | 最低通过条件 |
|---|---|---|
| S0 小修复 | 简单需求是否被过度流程阻塞？ | 能快速得到范围、修改和验证结果 |
| S1 普通 Feature | 正式流程是否减少遗漏而非增加文档？ | 全程可恢复，每个保留阶段都有决策价值 |
| S2 跨模块需求 | 复杂流程是否发现影响面和交付缺口？ | 关键风险、影响面、验收和未完成项都有证据 |

### 场景验证顺序

1. 先由外部验证者写独立验收标准；
2. 保存用户原始需求，不提前技术化；
3. 让当前引擎处理，不中途为它修复；
4. 记录引擎输出、用户修正、流程负担和错误；
5. 用独立命令、diff 和测试验证结果；
6. 场景结束后才决定保留、修改、合并或删除能力。

## 3. 工程路线与产品路线

产品上最先需要的是 `Explore → Clarify → Reassess → Route`；工程上必须先提供能保存这些信息的状态基础。因此路线如下：

### 阶段 A：状态可信

目标：新 Feature 有唯一、可恢复、可审计的结构化状态。

范围：

- `workflow-state.json` 唯一事实源；
- `schemaVersion`、revision、history、currentStage；
- 原子写入和陈旧更新拒绝；
- 明确失败，不从 Markdown、YAML 或旧事件恢复；
- 旧 Feature 不迁移、不回放、不兼容。

不包含：split、Quick 路由、旧数据清理之外的兼容、Graph Coding。

**退出条件**：状态测试通过，三类场景能保存和恢复最小上下文，失败状态不被破坏。

### 阶段 B：需求理解与澄清 MVP

目标：用户不知道如何描述需求时，系统能帮助继续，而不是直接阻塞或猜测。

范围：

- Explore 识别需求、事实、风险和缺口；
- 生成结构化 `clarification-pack`；
- 支持部分回答和多轮记录；
- 保留问题、答案、假设、证据和轮次；
- 回答后重新评估；
- 输出唯一 `nextAction`。

**退出条件**：S1 场景能从信息不足恢复到明确路由，用户不需要重复输入已确认内容。

### 阶段 C：路由和轻量路径

目标：简单任务不过重，复杂任务不走捷径。

范围：

- 所有自然语言需求先经过 Explore；
- `quick` 只能消费已确认的低风险、小范围上下文；
- `feature` 进入正式流程；
- `split-candidate` 先进入正式决策，不直接拆分；
- 越界、风险扩大或影响面扩大时升级；
- 权限/环境问题与普通需求不清晰区分。

**退出条件**：S0 和 S1 场景都能得到正确路由，且用户负担没有明显增加。

### 阶段 D：split 聚合

目标：多个独立交付面有明确父子状态和聚合门禁。

前置：阶段 A 稳定；阶段 B/C 已证明单 Feature 路由价值。

范围：

- 显式 `mode`、`aggregation` 和 execution scope；
- 父层不伪造阶段完成；
- 所有子 change 验证并合并后，父层只执行一次真实的后续阶段。

**退出条件**：S2 或真实多交付需求复现 split 价值，并有独立回放证据。

### 阶段 E：效率和治理

只有前面场景证明价值后再启动：

1. 真增量扫描和无变更短路；
2. 架构信号注入 `scope/plan/converge/verify`；
3. 知识价值阈值；
4. `--json` 全覆盖和 CI 模板；
5. Skills 多 binding、reference 按需加载。

## 4. 当前 Backlog 的重分类

| 原 Backlog 项 | 产品归属 | 当前决策 |
|---|---|---|
| R1.1 Workflow v3 状态核心 | 状态可信 | 保留，作为工程底座 |
| R1.2 split 聚合 | 多交付治理 | 延后到真实需求证明后 |
| R1.3 Explore→Quick | 需求路由 | 在状态基础后优先验证 |
| P1-6 真增量扫描 | 效率 | 延后，不把“过滤”误称为增量扫描 |
| P1-4 知识价值阈值 | 知识质量 | 延后到真实复用证据出现 |
| P2-12 架构信号注入 | 交付治理 | S2 场景证明遗漏后再做 |
| `--json` 全覆盖 | 集成基础 | 作为机器消费需求出现时再做 |
| Graph Coding | 战略能力 | 暂缓，不能用来解决当前方向混乱 |
| MCP、Cursor、联邦 Hub | 扩展能力 | 暂缓，无当前 MVP 证据 |
| 外部 Skills 吸收 | 方法增强 | 先做审计，不进入主线 |

## 5. 每个 Feature 的开发门

### 开始前

- 对应一个已复现的用户问题；
- 完成产品目标、范围和验收；
- 明确不做什么；
- 能说明它属于哪一个路线阶段；
- 不依赖已废弃的旧 Feature 或旧状态。

### 实施中

- 先写失败测试或独立验收；
- 每次只推进一个明确需求；
- 不顺带修复无关旧流程；
- 记录产品观察和工程缺陷，不把两者混为一谈。

### 完成前

- TypeScript 检查；
- 定向测试；
- 完整测试并记录失败分类；
- 独立场景验收；
- 新会话恢复验证；
- 最终 diff 和范围审查。

### 完成后

只有当用户价值证据成立，才允许把能力标记为稳定并继续下一个 Feature。否则结论必须是：修改、合并、降级或删除。

## 6. 暂停规则

出现以下任一情况，停止扩展能力，回到产品诊断：

- 用户无法说清当前该开发什么；
- 阶段产物越来越多但决策质量没有提升；
- 同一事实在多个文件中出现且无法确定真相；
- 为了旧测试全绿而恢复已废弃协议；
- 新功能没有真实用户场景和独立验收；
- 引擎输出无法区分事实、假设和建议。

## 7. 下一步唯一动作

建立并执行 S0、S1、S2 三份外部场景记录。场景完成前不新增主线 Feature，不继续扩展 split、Quick、Graph、MCP 或 Skills。
